# tts_batch_max_items：NPU 参数验证报告

实机实验：2026-09-07；回归补充：2026-09-11。

## 参数用途与验证目标

一条语音任务是提交一段文字并生成对应音频。批量接口允许一次提交多条任务；`tts_batch_max_items` 限制一次请求最多包含多少条，默认值为 32。

本次要确认：NPU 服务是否仍需要数量限制，修改上限是否真正生效，以及合法批次是否能完成生成并返回对应结果。

| 项目 | 说明 |
| --- | --- |
| NPU 是否需要 | 需要。保留批量提交，就需要控制一次接收的任务数量 |
| 实现方式 | 共用服务代码检查批量数量，合法任务随后进入模型处理 |
| 实机范围 | Fun-CosyVoice3-0.5B-2512、Ascend910、本次归档配置；引擎最多同时运行 2 条请求 |
| 参数不代表什么 | 一次可提交 32 条不等于同时计算 32 条，也不是设备内存上限 |
| 结论 | 所测配置下，上限和修改设置生效，合法批量生成完成；无需新增 NPU 专用参数逻辑 |

## 测试方法与结果

这个参数规定“一次最多接收多少条任务”。要确认它生效，首先需要围绕上限检查三种情况：少于上限、刚好达到上限、超过上限。前两种应该正常生成，后一种应该因数量超限被拒绝。只测很小的请求或很大的请求，无法判断服务是否在正确的位置划定了界限。

还需要改变一次上限。如果服务内部把上限固定写死，即使前一组请求都得到预期结果，也不能证明用户设置的参数被采用。因此，把上限调大后，应当看到原来被拒绝的数量变得可接受，同时新的超限请求仍被拒绝。这是区分“数量检查存在”和“参数修改生效”的关键。

具体测试先将上限设为 2，提交 1、2、3 条任务；再改为 3，提交 3、4 条。这里用较小的数量便于逐项核对，随后再测试默认上限 32。数量允许只是第一步，用户还应收到每条文字对应的音频，所以还检查重复生成、错误条目的处理，以及结果是否漏项或错位。最后将音频转回文字，记录内容差异，不把“文件存在”直接当成“内容正确”。

下表中的回归测试用于在代码修改后重新检查这些规则；人为丢失参数时，预期结果与实际结果不一致、触发“断言失败”，说明测试能发现这一错误。

| 要确认什么 | 具体怎么测 | 通过标准 | 实际结果 |
| --- | --- | --- | --- |
| 上限内生成、超限拒绝 | 上限 2，分别提交 1、2、3 条；另测空请求 | 1、2 条完成生成，3 条因超限被拒绝，空请求被拒绝 | 全部符合预期 |
| 修改上限实际生效 | 改为上限 3，提交 3、4 条 | 原来超限的 3 条现在成功，4 条仍被拒绝 | 3 条全部生成，4 条被拒绝 |
| 默认上限正确 | 不配置参数，提交 31、32、33 条 | 前两者生成，33 条被拒绝 | 全部符合预期 |
| 重复批量生成可完成 | 默认上限下，1/2/4/8/16/32 条各重复 3 次，另测 31 条一次 | 每项成功并返回结构完整的音频 | 19 次批量请求、220 条任务全部完成；不是逐字正确性结论 |
| 错误项不混淆其他结果 | 合法数量中混入错误条目，另测全部错误及错误后的合法请求 | 分清每项成功/失败，服务可以继续处理 | 对应检查通过 |
| 文件与记录不漏项、不串位 | 同一组 32 句话，先逐条生成，再一次批量生成 | 每条记录有对应的完整文件 | 共 64 份音频，文件结构与记录对应检查通过 |
| 内容是否有差异 | 用 Whisper small 转写上述 64 份音频，统一数字表达后与输入比较 | 如实记录不一致项，不以文件完整代替内容正确 | 逐条 29/32、批量 28/32 完全一致；其余有差异，不能直接归因于批量参数 |
| 非法配置被拒绝 | 启动时设置 0、负数、非整数 | 明确拒绝非法设置 | 3 项启动检查通过；后续 CPU 回归也覆盖此规则 |
| 回归测试能发现参数丢失 | 人为把传出的自定义上限改回 32 | 既有配置测试断言失败 | 1 个断言失败，故障被检出 |

## 量化结果与结论边界

| 项目 | 结果及解释 |
| --- | --- |
| 短句处理速率 | 本次约 0.755 条/秒；不是隔离性能基准，也没有 CUDA 对照 |
| 设备进程内存 | 采样观察最大值 4,087 MB；可能遗漏瞬时峰值，不是参数承诺的内存上限 |
| 音频内容 | 文件完整、记录对应不等于每个字都读对；转写差异可能来自模型生成或识别器 |
| 支持范围 | 证明所测配置的数量限制和合法批量生成；不证明调大上限会提速、所有模型可用或两种请求方式音质完全相同 |
